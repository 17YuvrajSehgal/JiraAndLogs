## 1. The snapshot

The code already did the right thing: `snapshot_sha = first["parent"]`,
and `02-benchmark.tex` already said so precisely. The problem was one
sentence in the introduction claiming the agent sees *"the code as it was
when the issue was open"*. That is false, and the same paragraph then
contradicted it. Removed.

`02-benchmark.tex` now states the consequence plainly: the parent of the
fix commit is a **known-defective revision**, not the revision deployed
when the report was filed, and the two differ by whatever else landed in
between. We measure localization on a revision that contains the defect,
which is the setting the challenge describes, and we make no claim about
replaying the exact tree an engineer faced at triage.

The distinction that matters for a reviewer: report-time admissibility is
claimed only for the **incident memory**, and enforced there. It was never
claimed for the code snapshot.

## 2. Post-fix content in descriptions

This was the right thing to be worried about, and nothing in the pipeline
guarded against it. The query text comes from a Jira dump taken long after
these bugs were fixed, and Jira descriptions are mutable.

`scripts/description_leak.py` is now the single home for the rule.

**What is in there.** Unambiguous post-fix artifacts — a diff or patch
block, a link to a commit or pull request, "fixed in/by", "resolved by",
"patch attached", a review-board link:

| | count | share |
|---|---|---|
| unambiguous post-fix artifact | **364 of 6,314** | **5.8%** |
| commit link | 142 | |
| "fixed in/by" phrasing | 125 | |
| diff or patch block | 67 | |
| review link | 44 | |
| bare commit SHA only — **kept** | 793 | |

The bare SHA is deliberately not counted as contamination. Bug reports
routinely name the commit that *introduced* a regression, which is
legitimate report content and is most of the SHA mentions here. Counting
it would have inflated the figure to 18.4%.

**What dropping them costs.** Every system re-scored on the clean subset,
no re-runs, since all rankings were already stored:

| population | system | all | clean | contaminated only | delta |
|---|---|---|---|---|---|
| eval split (4,409 → 4,140) | `cond_ours` | 68.63% | 68.72% | 67.29% | +0.09 |
| the 790 | `remember` | 90.25% | 90.40% | **88.52%** | +0.14 |
| the 790 | `llm_rerank` | 77.97% | 79.15% | 63.93% | +1.17 |

**The direction is the argument.** If a post-fix artifact were acting as
an answer key, those instances would be *easier*. On the study population
every system scores **lower** on them than on the clean ones. REMEMBER
drops from 90.4% to 88.5%; the model re-ranker drops 15 points. The
largest movement from dropping them is 1.17 points, on `llm_rerank`.

One honest nuance: the pure path signals (`trace_grep`, `path_bm25`) do
score slightly *higher* on the contaminated instances, 43.5% against
39.7%. That is exactly where a pasted patch containing file paths would
help, so the effect is visible where it should be and is small. It does
not reach the systems the paper's claims rest on.

## 3. An existing localization agent as a baseline

**Not done, and I do not think it fits the remaining time.** The current
baselines are rVSM, BugLocator, BRTracer-style, SimiScore, two LLM
pipelines and the fusion — all retrieval or single-shot. No published
agent.

The criticism is fair. Doing it properly means porting an existing agent
onto our snapshots, giving it the same model and a comparable inference
budget, and running it. That is a build plus GPU time, with the cluster
job still to be started. The plan is to state it as a limitation unless
time appears at the end.

## 4. Module accuracy, function level, explanations

**Module accuracy was genuinely missing.** The paper reported 66.9% module
Acc@1 for *the retrieval layer*, which is a component inside the agent,
not REMEMBER. The agent rows did not even carry `gold_modules`.

Now computed by `scripts/module_metrics.py --study790`, on the 790
instances REMEMBER ran:

| system | module Acc@1 | Acc@5 | MRR | hard Acc@1 |
|---|---|---|---|---|
| Lexical log-to-code | 75.1% | 96.7% | .843 | 69.1% |
| Retrieval + memory | 80.8% | 97.1% | .877 | 71.2% |
| Model re-rank | 90.5% | 96.1% | .931 | 83.5% |
| Model alone | 91.1% | 95.3% | .931 | 86.7% |
| **REMEMBER** | **94.2%** | **98.9%** | **.963** | **90.4%** |

REMEMBER leads every system on every column. This was simply not being
reported.

Two populations are kept separate, because the three IRBL baselines stored
rankings only for the causal-gold subset and cover just 93 of the 790. The
nine-way comparison is reported at n=93 and the six-way at n=790; neither
stands in for the other.

**Function/region on the same instances** is T20 in the review-2 tracker
and needs the full run first. **Explanations judged by two annotators with
agreement before adjudication** is T16–T18 there. Worth flagging: we hit
exactly that problem in T2b. No second human annotator was available, so
the causal-gold agreement number is model-vs-model (kappa 0.885) and is
reported as such, never as human reliability.

## 5. The memory index

Correct, and it was a real hole. The firewall ran at the wrong stage.

v2 built the BM25 index **once per project over the whole pool** (MongoDB:
19,819 incidents, including ones resolved years after the query's report),
ranked the top 50, and only then dropped inadmissible hits. Two separate
problems: `idf`, `df` and `avgdl` were computed across documents that did
not exist yet, and inadmissible incidents occupied slots in the ranked
pool so admissible ones were crowded out before the filter ran.

`scripts/memory_index_leak.py` measures it against the correct
construction, n=500:

| | |
|---|---|
| inadmissible share of the ranked pool | **50.4%** |
| instances returning fewer than k=5 incidents, v2 | **7.4%** |
| same, with the admissible-only index | 1.2% |
| returned top-5 identical | 72.4% (mean overlap 4.51/5) |
| **a gold file reachable from memory** | **50.4% now vs 50.6% fixed** |

So the ranking genuinely changes on about a quarter of instances, and the
crowding starves 7.4% of them — but it does not change whether memory can
reach a gold file, and the correct construction is very slightly *better*.
The leak was never inflating our numbers.

**Fixed in v3 anyway.** `Workspace.strict_memory_firewall` builds the index
from the admissible incidents of that instance alone. The original
justification for the shortcut was speed; it does not survive measurement:
filtering and rebuilding costs 0.06–0.12 s even on MongoDB's pool, against
232 s of wall time per instance. v2 is untouched, so every reported number
still reproduces.
